# System Architecture & Implementation Plan: Production WireGuard Relay for Ollama

This document serves as a comprehensive technical specification and requirements blueprint for building a secure, hub-and-spoke WireGuard VPN network using **Hetzner Cloud** and **Terraform**. 

The goal of this architecture is to connect remote developers in India to a home-hosted Linux server running Ollama, utilizing a flat-rate cloud VPS as a secure traffic relay. This eliminates the need for dynamic DNS adjustments, home router port forwarding, or public exposure of the home network.

---

## 1. Architectural Overview

The network implements a **Hub-and-Spoke Topology** managed by a single WireGuard instance running inside a Docker container (`wg-easy`) on a Hetzner Cloud VPS.

[ Developer 1 (India) ]         [ Developer 2 (India) ]
    (10.0.0.3) Split-Tunnel         (10.0.0.4) Split-Tunnel
               \\                               //
                \\                             //
                 ▼                             ▼
         ===============================================
         [          Hetzner Cloud VPS (Hub)            ]
         [  Public IP: vpn.skillrev.in | 10.0.0.1      ]
         [  Admin UI: Bound strictly to 127.0.0.1:51821 ]
         ===============================================
                                ▲
                                │ (Permanent Outbound Tunnel)
                                │ (PersistentKeepalive = 25)
                                ▼
                 ===============================
                 [   Home Linux Server (Spoke) ]
                 [   Internal VPN IP: 10.0.0.2  ]
                 [   Service: Ollama (11434)    ]
                 ===============================

### Core Security Design (Option B: Complete Admin Isolation)
To protect the network from discovery and brute-force attacks, the `wg-easy` web administration dashboard (Port `51821`) **must not be exposed to the public internet**. 
* The dashboard port will be bound explicitly to `127.0.0.1:51821` on the VPS host machine.
* To access the dashboard, the administrator must establish a secure SSH local port-forwarding tunnel (`ssh -L 51821:127.0.0.1:51821 user@vps`). This ensures that administrative access requires valid cryptographic SSH private keys, rendering the web interface completely invisible to public scanners.

## 2. Terraform Requirements & Resource Schema

The Terraform configuration must target the Hetzner Cloud (`hcloud`) provider and fully automate infrastructure creation, network firewall rules, and software provisioning.

### 2.1 Variables Input Definition
The Terraform module must expose the following configurable variables:
* `hcloud_token`: API token for Hetzner Cloud authentication (sensitive).
* `server_type`: The instance size (Default: `cx22` or lowest tier x86/ARM instance).
* `location`: The target datacenter location (e.g., `fsn1` for Falkenstein, Germany, or `ash` for Ashburn, VA, USA).
* `image`: Operating system image (Default: `ubuntu-24.04`).
* `admin_ssh_key_name`: Identifier for the public key inside Hetzner.
* `admin_ssh_public_key`: The raw public key string allowed to access the host via SSH.
* `wgeasy_admin_password`: The plain-text master password for the WireGuard dashboard (used to compute the login hash).

### 2.2 Hetzner Cloud Resources to Provision
1. **`hcloud_ssh_key`**: Registers the administrator's public key to allow passwordless root login.
2. **`hcloud_firewall`**: Establishes strict network perimeter security.
3. **`hcloud_server`**: Deploys the virtual machine, applying the firewall, SSH keys, and provisioning script.

### 2.3 Network Firewall Matrix
The `hcloud_firewall` resource must enforce the following packet filtering rules:

| Direction | Protocol | Port / Range | Source / Destination | Description |
| :--- | :--- | :--- | :--- | :--- |
| **Inbound** | UDP | `51820` | `0.0.0.0/0`, `::/0` | WireGuard VPN Tunnel Traffic |
| **Inbound** | TCP | `22` | `0.0.0.0/0` (or restricted CIDR) | Administrator Emergency SSH Access |
| **Inbound** | Any | Any | Drop All Other | Default Deny Rule |
| **Outbound**| Any | Any | `0.0.0.0/0`, `::/0` | Allow all outbound traffic |

*Note: Port `51821` (Web UI) is deliberately absent from the firewall rules because it binds directly to the local loopback interface, completely bypassing external network ingress.*

## 3. Provisioning & Cloud-Init (`user_data`) Specifications

The Terraform setup must use a shell script or Cloud-Init configuration passed into the `user_data` argument of the `hcloud_server` resource to fully automate the software stack instantiation on first boot.

### 3.1 Kernel Modifications
The script must persistently enable IPv4 packet forwarding to allow the VPS to route data packets between the separate WireGuard peers (the home server and remote developers):
```bash
sysctl -w net.ipv4.ip_forward=1
echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf

3.2 Dependencies Installation
Update apt repositories and upgrade existing system software.

Install necessary system utilities: curl, git, iptables.

Install the official Docker Engine and Docker Compose plugin following Docker's official modern installation guidelines (avoiding deprecated docker-compose legacy binaries).

3.3 Docker Compose Architecture (wg-easy)
The provisioning layer must create an isolated working directory at /opt/wg-easy and generate a docker-compose.yml file with the exact specifications below:

```
version: '3.8'

services:
  wg-easy:
    environment:
      # Core Network Settings
      - LANG=en
      - WG_HOST=${vps_public_ip} # Explicitly use VPS public IP
      - PORT=51821
      - WG_PORT=51820
      - WG_DEFAULT_ADDRESS=10.0.0.x # Explicitly specify custom internal IP pool
      - WG_DEFAULT_DNS=1.1.1.1,8.8.8.8
      - WG_ALLOWED_IPS=10.0.0.0/24
      
      # UI Authentication (Password must be pre-generated using bcrypt via provisioning)
      # NOTE: Ensure all '$' symbols inside the resulting string are doubled up to '$$' for Docker Compose validation.
      - PASSWORD_HASH=${wgeasy_password_hash}
      
      # Keepalive to ensure NAT holes through home routers remain open
      - WG_PERSISTENT_KEEPALIVE=25
    image: ghcr.io/wg-easy/wg-easy
    container_name: wg-easy
    volumes:
      - .:/etc/wireguard
    ports:
      - "51820:51820/udp"
      # OPTION B ENFORCEMENT: Force the UI to listen ONLY on the host loopback interface
      - "127.0.0.1:51821:51821/tcp"
    restart: unless-stopped
    cap_add:
      - NET_ADMIN
      - SYS_MODULE
    sysctls:
      - net.ipv4.ip_forward=1
      - net.ipv4.conf.all.src_valid_mark=1
```

3.4 Automated First Certificate Generation ("The Bootstrap Profile")
Because the web interface is inaccessible upon deployment until an SSH tunnel is built, the user_data script must automatically seed or "mint" the first configuration profile (the Administrator's configuration profile) directly within the configuration storage layer, OR provide precise post-provisioning steps.

Since wg-easy stores client definitions inside /etc/wireguard/wg0.json, the script should:

Start the Docker containers via docker compose up -d.

Wait for the application to initialize.

Execute a local docker command or API query to generate a client profile named Network-Admin.

Extract the generated .conf profile data and save it to /root/network-admin-wireguard.conf on the host system for easy administrative extraction.

4. Client Profile Mapping Rules
The final solution must instruct the downstream AI code generation platform to account for three specific types of WireGuard peer architectures:

4.1 Home Linux Server Profile (The Ollama Host)
Internal IP Allocation: 10.0.0.2/24

Routing (AllowedIPs): 10.0.0.0/24. This configuration must allow the home machine to see traffic originating from any developer connected to the VPN subnet.

Keepalive Requirement: Must include PersistentKeepalive = 25 to continuously ping the Hetzner hub, keeping outbound firewall pinholes open indefinitely on the home router.

4.2 India Developer Profiles (The Remote Workers)
Internal IP Allocation: 10.0.0.3/24, 10.0.0.4/24, etc.

Strict Split Tunneling Rule (AllowedIPs): Must be configured strictly to 10.0.0.2/32. This guarantees that only traffic explicitly targeting the home server's internal VPN IP address travels through the encrypted tunnel. General web browsing, personal operations, and code deployment continue using their native, local ISP connections seamlessly.

5. Terraform Operational Outputs
Upon successful execution (terraform apply), the configuration must output the following clean diagnostic parameters to the terminal:

vps_public_ipv4: The raw public IP assigned by Hetzner to the VPS relay.

ssh_tunnel_command: A copy-pasteable terminal command for the administrator to establish secure access to the isolated panel:
ssh -L 51821:127.0.0.1:51821 root@<vps_public_ipv4>

admin_config_download_command: A copy-pasteable SCP command to pull the initial bootstrap administration VPN profile down to the admin's local desktop system:
scp root@<vps_public_ipv4>:/root/network-admin-wireguard.conf ./

next_steps_guide: Text outputs outlining how to configure the home Linux environment variables (OLLAMA_HOST=0.0.0.0) and use UFW firewalls locally to bind incoming traffic on port 11434 strictly to the wg0 interface.
